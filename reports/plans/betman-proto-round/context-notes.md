- 우리 1X2 픽(predWinner)이 있는 기본형 라인, 베트맨 판정 기준 적중: 260111 축구 57/123·야구 48/88, 260108 축구 51/118·야구 48/88.

  구매자가 보는 결과와 같아야 한다. 어긋나는 4%는 연장·정정·더블헤더 매핑 쪽.

## 베트맨 코드표 (raw 260112 + DB 대조로 확정)

| 필드 | 값 | 뜻 |
|---|---|---|
| `gameResult` | `0` / `1` / `2` / `4` / null | 승(win 쪽) / 무(draw 쪽) / 패(lose 쪽) / **적특(취소·환불)** / 미판정 |
| `protoStatus` | `1` / `2` / `3` / `4` | 발매예정 / 발매중 / 마감 / 결과발표 |
| `winTxt·drawTxt·loseTxt` | 승·무·패 / 언더·-·오버 / 홀·-·짝 / 승·1·패 | 라인 유형별 양쪽 이름 |
| `mchScore` | "0:3", 핸디는 "2.5:3" | 판정 스코어(핸디 적용값) — 새로 저장 |

- **언더오버는 `winAllot`=언더, `loseAllot`=오버.** 기존 `LineRow` 가 반대로 라벨을 붙이고 있었다(`winTxt` 로 확정, DB 대조 89%·99%).
- 승N패 가운데 결과(`1`)는 "N점차" — betNm `야구 승1패`·`농구 승5패` 에서 N 을 뽑는다.
- `gameResult='4'` 는 야구에 많다(선발 투수 변경 적특) — 성적표 분모에서 뺀다(정배당도 같은 규칙).

## 배당 변동 — 베트맨이 이력을 준다

`gameInfoInq.do` 응답 `tooltipList` = 회차 시작 이후 전 변경 이력. 260112 는 08:11~13:03 사이 36건(26라인).
```
GM_SEQ, CHG_DTM("20260921130320863455" KST), BCHG_W_ODDS/ACHG_W_ODDS (x100 정수: 159=1.59), D/L 동일,
BCHG_W_HANDI_RT/ACHG_W_HANDI_RT (핸디 라인 변경), L_HANDI 동일
```
→ 자체 스냅샷 테이블 대신 `BetmanOddsChange` 에 그대로 쌓는다. id = `{gmTs}-{seq}-{CHG_DTM 14자리}`, ON CONFLICT DO NOTHING.
워커는 하루 2회 그대로 — 이력은 회차 안에서 누적돼 오므로 빈도를 올릴 이유가 없다.
화면은 "회차 첫 배당 → 현재" 방향(▲▼)과 변경 횟수만. 이전 값은 title 로.

## 설계 결정

1. **회차 = URL 파라미터** `round=260111`. 없으면 종전대로 발매중 뷰. 회차 뷰는 `gameDate` 필터를 걸지 않는다(끝난 경기가 본체).
2. **AI 도장은 기본형만.** 핸디·OU 는 라인이 달라 후속. 예정 경기는 "AI 픽" 칩만.
3. **성적표는 순수 함수 + SQL 한 방.** `betman-result.ts` 에 prisma 를 넣지 않는다(순수함수·prisma 동거 함정, 9/11 감사).
4. 아카이브 회차의 `mchScore` 는 워커가 직전 1회차까지만 받아 채워지지 않는다 → `Match.homeScore/awayScore` 폴백.
5. 회차 라벨: gmTs 260111 → "2026년 111회차".
6. DDL 은 raw SQL(lock_timeout 3s) — `db push` 금지 원칙 유지.
