## 리그 코드 = HOCKEY_FRIENDLY (CLUB_FRIENDLY 재사용 불가)

`CLUB_FRIENDLY` 는 **이미 축구 클럽 친선 코드로 쓰이고 있다**. dry-run 에서 이름이 겹친 21개 Team row
(Slovan Bratislava·Red Bull Salzburg·Dynamo Moscow·Lausanne·Grenoble …)가 전부 축구 팀이었다.
같은 코드를 쓰면 하키 매치가 축구 팀 row 로 해석되고 /scores 종목 탭도 갈라진다.
배구 선례(`VB_FRIENDLY`)와 같은 종목 접두 규칙을 따른다.

## 동명 클럽은 하키 Team row 를 따로 만든다

Dynamo Moscow·Spartak Moscow·Slovan Bratislava 등은 축구 row 가 이미 있지만 **다른 종목의 다른 구단**이다.
배구 친선에서 기존 row 를 재사용한 것과 반대 판단 — 배구는 같은 "국가대표"였고 여기는 종목이 다르다.
로고·Elo·경기 이력이 전부 갈라져야 맞다.

부작용 주의. Team dedup 잡이 "이름 같은 두 row"를 중복으로 볼 수 있다. 리그 코드가 다르고
`scorebase-team-dedup` 은 리그 지정 실행이라 자동 오작동은 없지만, 하키 리그를 dedup 대상으로 돌릴 때
축구 row 를 끌어오지 않도록 리그 필터를 반드시 건다.

## 249팀 전량 시드 — 부분 매핑을 기각한 이유

collector 는 **양팀 모두** 매핑돼야 매치를 push 한다(`tsIdSet.has(home) && tsIdSet.has(away)`).
그래서 커버리지가 팀 비율의 제곱처럼 떨어진다. 실측.

```
상위  40팀 → 매치  60/320 (18%)      상위 120팀 → 194/320 (60%)
상위  80팀 → 매치 130/320 (40%)      상위 200팀 → 282/320 (88%)
상위 100팀 → 매치 165/320 (51%)      전체 249팀 → 320/320 (100%)
```

팀 시드는 어차피 스크립트 자동화라 249나 100이나 비용이 같다. 전량이 맞다.

## 팀명 해석 경로 — team/list 는 page 로 전량 열린다

기존 메모리에는 `team/list?uuid=` 단건만 적혀 있었지만, **`team/list?page=N` 이 1000건씩 전량
페이지네이션으로 열린다** (하키 총 3,565팀, 4페이지). 249팀 이름·로고·country_id 를 한 번에 확보했다.
`uuid=` 에 콤마 다중 전달은 `code=100003` 으로 거부되니 단건 아니면 페이지네이션.

## 예측·순위는 의도적으로 비운다

- 신규 249팀은 Elo 1500 시드 → PREVIEW 품질 게이트(양팀 1500 = 발행 skip)가 자동으로 막는다([[preview-quality-gate-elo]]).
  친선에 AI 프리뷰가 붙는 건 어차피 부적절하므로 그대로 둔다.
- 순위표는 하키 `season/table` 미인가 + 친선 자체가 순위 없음. 배구 친선에서 한 것처럼
  매치 상세의 "순위표 →" 링크가 뜨지 않는지 확인한다(소프트 404 방지).
