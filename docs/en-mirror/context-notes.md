# /en 자동 생성 미러 — 컨텍스트 노트

작업 중 내린 결정과 근거를 계속 덧붙인다.

---

## 2026-08-23 · 착수

### 왜 "영어가 한국어와 다른가" 의 진짜 원인

처음엔 번역 품질 문제로 보였으나, 실측해보니 구조 문제였다.
`src/app/en/` 은 한국어 페이지를 번역한 게 아니라 **사람이 새로 짠 13페이지짜리 별도 트리**다.
공유하는 건 root layout 과 `src/lib/i18n/en.ts` 사전뿐이고, 페이지 로직은 완전히 따로다.
그래서 한국어 쪽에 기능을 추가해도 영어는 영향을 안 받고, 시간이 갈수록 벌어진다.

### 자동 생성 미러를 고른 이유

정공법 i18n(문구를 전부 사전으로 빼고 소스 1벌로 두 언어 렌더)이 구조적으로는 정답이다.
하지만 한글이 걸린 파일이 1,252개 / 28,700줄이고, 운영은 1인이다.
이 규모를 손으로 치환하는 동안 사이트 기능 개발이 멈춘다 — 비용이 효과를 넘는다.

자동 생성 미러는 파일이 2벌이 되는 대신,
(1) 생성물을 눈으로 검토·수정할 수 있고
(2) 실패해도 한국어 원본이 안전하며
(3) 한국어 수정 후 스크립트 재실행 1번으로 동기화된다.

되돌리기 쉬운 쪽을 골랐다.

### 기존 수동 /en 13개를 안 건드리는 이유

이미 품질이 확보돼 있고, 자동 생성으로 덮으면 퇴행 위험이 있다.
자동 생성은 **비어 있는 29개를 채우는 데만** 쓴다.
나중에 자동 생성 품질이 수동본에 근접한다고 판단되면 그때 통합을 검토한다.

### 대상 29개 선정 근거

메모리의 실측(`project_ranking_blog_formula`)에 따르면
"표 30행 + 고유명사 다수" 페이지가 검색에서 롱테일을 잡는다.
그래서 연봉 랭킹 8종과 랭킹 4종을 우선 넣었고,
나머지는 축구 데이터 페이지 중 고유명사 밀도가 높은 것으로 골랐다.

### AST 로 처리하는 이유

정규식으로 한글을 치환하면 주석·문자열·JSX 텍스트를 구분 못 해서 오작동한다.
특히 템플릿 리터럴 안 한글(`` `${team} 승리` ``)은 정규식으로 안전하게 못 다룬다.
TypeScript AST 로 노드 종류를 보고 치환한다.

### 미해결 / 다음 판단이 필요한 것

- **DB 발 한글** — 기사 본문, 한글화된 팀·선수명은 소스 치환으로 안 잡힌다.
  1차 범위는 UI 라벨만. DB 쪽은 별도 과제.
- **조사 처리** — `josa()` 가 붙은 동적 문장은 영어에서 불필요하고 어색해진다.
  개별 확인 대상으로 남겨둔다.

## 2026-08-23 · Phase 1 도중 — 규모 재산정

### 페이지만으로는 안 된다 (공용 컴포넌트 층 발견)

`/salaries/golf` 프로토타입을 짜다 `PlayerValueTabs` 가 한글 라벨과 한국어 링크를
그대로 들고 있는 걸 발견했다. 페이지만 미러링하면 영어 페이지 안에 한국어 탭이 남는다.

29개 페이지가 끌어쓰는 공용 컴포넌트 35개를 조사한 결과, **30개가 렌더 경로에 한글을 갖고 있다**
(약 600줄). 즉 작업은 페이지 층 + 컴포넌트 층 두 겹이다.

| 층 | 개수 | 한글 |
|---|---|---|
| 페이지 | 29 | 1,731줄 |
| 공용 컴포넌트 | 30 | ~600줄 |

### 컴포넌트를 lang prop 이 아니라 미러로 처리하는 이유

두 안을 놓고 골랐다.

- **lang prop 추가** — 파일 1벌 유지, 정석. 하지만 컴포넌트 30개를 손으로 고쳐야 하고
  (`lang === "en" ? ... : ...` 삼항이 600줄 어치 퍼진다) 한국어 동작을 건드리는 만큼
  회귀 위험이 생긴다.
- **미러 복제** — 페이지에 이미 적용 중인 방식과 일관되고, 같은 스크립트로 자동화된다.
  무엇보다 **원본을 전혀 안 건드리므로 한국어 사이트가 깨질 수 없다**.

미러로 간다. 페이지에서 이미 "되돌리기 쉬운 쪽" 을 골랐으니 컴포넌트도 같은 기준을 따른다.

### 그에 따른 스크립트 설계

1. 페이지에서 시작해 `@/components/**` import 를 **재귀적으로** 수집
2. 렌더 경로에 한글이 있는 것만 미러 대상 (없으면 원본 그대로 재사용 — 파일 중복 최소화)
3. 미러는 `src/components/en/<원래경로>` 에 생성
4. import 경로는 미러가 존재할 때만 `@/components/en/...` 로 치환

### 프로토타입을 /salaries/golf 로 잡은 이유

가장 작고(160줄), 쓰는 컴포넌트 3개 중 한글 렌더는 `PlayerValueTabs` 하나(5줄)뿐이라
페이지 층과 컴포넌트 층을 **둘 다** 통과시키면서도 검증 범위가 작다.
여기서 파이프라인 전체가 돌면 나머지는 규모만 늘어난 반복이다.

## 2026-08-23 · Phase 1 완료 — 파이프라인 실증됨

`/salaries/golf` 로 끝까지 통과시켰다. 한글 34건 → 미번역 0건, tsc 통과, dev 렌더 확인.

### 실측으로 확인된 것

- 한글 34건 중 **24건은 번역이 아니라 코드 제거로 해결됐다**.
  원화 환산·한글 선수명·한국 선수 색강조는 영어판에 존재할 이유가 없는 기능이다.
  즉 이 작업은 "번역" 보다 "한국어 전용 기능 걷어내기" 의 비중이 크다.
- 의존성 추적이 의도대로 작동 — 컴포넌트 3개 중 `PlayerValueTabs` 만 미러 대상,
  `AmbientGlow`·`PlayerPhoto` 는 한글이 없어 원본 재사용으로 분류됐다.
  덕분에 파일 중복이 최소화된다.

### 페이지당 드는 손

`/salaries/golf` (160줄, 가장 작은 페이지)에 보정 규칙 22건 + 사전 6건이 필요했다.
페이지 크기에 비례하므로 `/transfers/[id]` (1,368줄) 같은 건 훨씬 많이 든다.
**자동 생성이라도 페이지별 판단은 사람이 해야 한다** — 스크립트는 그 판단을
재생성 가능한 형태로 붙잡아 두는 역할이다.

### 보정 규칙을 JSON 으로 분리해 둔 값어치

한국어 원본을 고쳐도 `build.ts` 재실행 한 번이면 영어가 따라온다.
규칙이 원본과 안 맞으면 `[preReplace 미적용]` 경고가 떠서 조용히 깨지지 않는다.
이게 "손으로 짠 /en" 이 벌어졌던 문제의 해법이다.

## 2026-08-23 · 연봉 랭킹 7종 완료 + KBO 불가 판정

golf · soccer · mlb · nba · nhl · f1 · tennis 완료. 전부 미번역 0건, tsc 통과, 렌더 검증 통과.

### KBO 는 만들 수 없다 (데이터 문제)

`/salaries/kbo` 는 선수명·팀명·포지션이 **전부 한글 원본**이다.
DB 에 영문명이 아예 없어서, 미러를 만들면 "영어 껍데기 + 한국어 표" 가 된다.
저품질 페이지가 색인되면 SEO 에 오히려 해로우므로 이번 범위에서 제외했다.

다른 종목은 DB 가 영문을 들고 한글을 매핑으로 덧씌우는 구조라(golf·f1·tennis·mlb·nba·nhl)
매핑만 벗기면 됐다. KBO 만 방향이 반대다.

되살리려면 KBO 선수·구단 영문명 매핑이 먼저 필요하다 — 별도 과제.
그때까지 `PlayerValueTabs` 영어판에서 KBO 탭을 뺐다 (죽은 링크 방지).

### 검증 스크립트를 따로 만든 이유 (verify.ts)

처음엔 `grep` 으로 생성된 HTML 의 한글을 셌는데 페이지마다 1,185자가 잡혔다.
본문은 완전한 영어였고, **Next.js 가 RSC payload 를 `<script>` 에 직렬화해 넣은 것**이었다.
script/style 을 걷어내고 태그를 벗겨야 "사용자 눈에 보이는 한글" 만 남는다.

이 스크립트가 실제로 누출 2건을 잡았다 — `SOCCER_SALARY_SOURCE`·`F1_SALARY_SOURCE`.
**페이지가 아니라 데이터 JSON 의 `source` 필드가 한글**이라 페이지 변환으로는 안 잡히던 것.
한국어 원본을 건드리지 않으려고 영어판에서만 문자열로 대체했다.

### 함정 기록

- **JSX 는 `</strong>` 뒤 줄바꿈을 공백 없이 붙인다.** 한국어에서는 "추정치(2026-05-03 기준)" 로
  자연스러웠지만 영어는 "estimates(as of ...)" 가 된다. `{" "}` 를 명시해야 한다.
- **숫자 바로 뒤 문구**도 같은 함정. `top {n}players` 가 됐다. 사전 값 앞에 공백을 넣어 해결.
- **보정 규칙은 전역 치환**이라 들여쓰기만 다른 같은 문자열이 있으면 앞 규칙이 둘 다 지운다.
  결과는 맞을 수 있지만 우연이므로 `[미적용]` 경고가 뜨면 반드시 생성물을 확인할 것.
- **tsc 의 `incremental: true` 캐시가 stale 해지면** 엉뚱한 파일에 `TS2393 Duplicate function`
  이 뜬다. 코드를 고치기 전에 `tsconfig.tsbuildinfo` 를 지우고 다시 돌려볼 것.

## 2026-08-23 · 랭킹 4종 완료 — 빌더 한계 두 가지를 고침

### 로컬 컴포넌트를 놓치고 있었다

`/rankings/ufc` 가 `./UfcRankingsView` 를 쓰는데, 의존성 추적이 `@/components/**` 만 보고 있어
영어 페이지 안에 한국어 UI 가 통째로 남을 뻔했다.

대상 페이지를 전수 조사하니 3곳이 로컬 컴포넌트를 쓴다 —
`/rankings/ufc`(1개) · `/ballon`(2개) · **`/transfers/[id]`(17개)**.
`build.ts` 에 로컬 컴포넌트 미러를 추가했다. 미러는 `src/app/en/<route>/` 에 같은 이름으로 놓이므로
상대 import 는 재계산하지 않고 그대로 둔다(`rewriteRelativeImports` 에서 제외).

### DB 에만 있는 한글은 소스 치환으로 못 잡는다

UFC 체급명(`MmaRanking.displayName`)이 한글로만 저장돼 있다.
페이지에 매핑 객체를 넣으려 했더니 **키가 한글이라 추출기가 "미번역" 으로 잡았다** — 당연한 결과다.
`src/lib/i18n/en.ts` 에 `UFC_WEIGHT_CLASS_EN` / `enWeightClass()` 로 옮겨 페이지 소스에서 한글을 없앴다.
앞으로 DB 발 한글은 이 사전 파일에 모은다.

파이터 이름은 `RankedFighter` 가 `name`(영문)·`nameKo` 를 둘 다 들고 있어 문제없었다.
KBO 와 달리 영문 원본이 살아 있는 구조.

### 보정 규칙 검증기의 결함 (mkrule.py)

규칙을 쓸 때 매번 **원본 소스**와 비교해 존재를 확인했는데,
`build.ts` 의 `applyRules` 는 규칙을 순서대로 적용한다.
그래서 "앞 규칙이 바꿔놓은 자리를 노리는 규칙" 이 거짓 불일치로 잡혔다.
검증도 순차 적용으로 바꿔야 한다 — `/tmp/mkrule.py` 의 `Rules` 클래스가 그 역할.

### 주의: 검증 요청이 몰리면 rate-limit 에 걸린다

`verify.ts` 를 연달아 돌리면 middleware 의 rate-limit 이 429 를 준다.
한 번에 검사하는 라우트 수를 줄이거나 사이를 띄울 것.

## 2026-08-23 · 재생성 약속이 실제로 시험받았다 (그리고 통과했다)

한국어 원본 17개에 역방향 hreflang(`languages: koEnLanguages(...)`)을 넣었더니
영어판 재생성이 **깨졌다**. 이 구조의 핵심 약속("한국어 고치면 스크립트 한 번")이
처음으로 시험받은 순간이라 원인을 정확히 기록해 둔다.

### 무엇이 깨졌나

`[preReplace 미적용]` 경고가 15건 떴다. 원인은 두 가지였다.

**(1) 앵커를 너무 크게 잡았다.**
metadata 규칙이 title·description·keywords·alternates 를 **한 덩어리로** 앵커에 담고 있어서,
alternates 한 줄이 여러 줄로 바뀌자 전체가 어긋났다.
→ 각 override 의 앵커에서 옛 `alternates: { canonical: ... },` 한 줄을
   현재 소스의 새 블록으로 치환하는 스크립트로 일괄 갱신했다.

**(2) 전역 치환이 새로 생긴 코드까지 삼켰다.**
NHL override 에 링크용 `"/salaries/nhl"` → `"/en/salaries/nhl"` 전역 치환이 있었는데,
한국어 원본에 새로 생긴 `koEnLanguages("/salaries/nhl", ...)` 의 인자까지 바꿔버려
뒤따르는 metadata 규칙의 앵커가 사라졌다.
→ **좁은 앵커 규칙을 전역 치환보다 앞에 두는 것**으로 해결.

**(3) 중복 import.**
원본이 `koEnLanguages` 를 import 하게 되자 override 의 import 추가가 중복이 됐다.
→ 원본에 이미 있으면 규칙에서 빼도록 정리.

### 배운 것 — 보정 규칙 작성 원칙

- **앵커는 가능한 좁게.** metadata 를 통째로 잡지 말고 title·description·alternates 를 나눠 잡는다.
- **전역 치환(경로·심볼)은 배열 뒤쪽에.** 좁은 앵커 규칙이 먼저 소비하게 한다.
- **경고를 무시하지 말 것.** `[preReplace 미적용]` 이 없었다면 metadata 가 한국어인 채로
  영어 페이지가 나갔을 것이다. 미번역 0건·tsc 통과였어도 잡히지 않았다.

결과적으로 전체 재생성이 미번역 0건·미적용 0건으로 통과했고,
한국어↔영어 hreflang 도 양방향으로 출력되는 것을 실측 확인했다.

## 2026-08-23 · 감독 페이지 — 데이터 언어를 소스별로 따져야 했다

`/coaches/[id]` 는 한 페이지 안에서 데이터 소스마다 언어가 달랐다.
처음 렌더 검증에서 한글이 76건 나왔고, 소스를 하나씩 갈라보니 이렇게 나뉜다.

| 소스 | 언어 | 처리 |
|---|---|---|
| `team-coaches.json` | name(영문) + nameKo | name 사용 |
| `TacticalManagerContext` | name + nameKo **둘 다** | name 사용 (팀·감독·선수·슈터 전부) |
| `coach-honors.json` | **영문** | 그대로 |
| `coach-careers.json` | **한글 전용** (273명 전원, 영문 필드 없음) | 섹션 제외 |
| 전술 연구 아티클 | 한국어 기사 | 목록 제외 |

### 경력 타임라인을 빼도 페이지가 서는 이유

`coach-careers.json` 에 영문이 아예 없어 경력 타임라인·선수 시절은 낼 수 없다.
그런데 원본 코드에 이미 **폴백이 있었다** — `coachTimeline.length === 0` 이면
우승 기록(HONORS, 영문)을 클럽별로 보여준다.
그래서 `coachTimeline` 을 빈 배열로 두는 것만으로 폴백이 자연스럽게 뜬다.

남는 페이지도 빈약하지 않다. 전술 대시보드(포메이션 사용 분포·평균 포지션 피치·샷맵·월별 xG),
시즌 기록, 교체 성향, 최근 선발 XI 가 전부 영어로 나온다 — 오히려 데이터 밀도가 높은 쪽이 남았다.

### 교훈

**"이 페이지는 불가"를 소스 단위로 판단하라.** 한글이 나온다고 페이지를 통째로 포기하면
살릴 수 있는 걸 버린다. 반대로 한 소스가 한글이라고 그대로 내보내면 저품질 페이지가 된다.
76건 → 53 → 11 → 0 으로 줄여가며 각 소스의 영문 유무를 확인하는 게 맞았다.
