# /en 자동 생성 미러 — 계획

## 문제

`/en` 은 한국어 페이지의 번역본이 아니라 **손으로 따로 짠 별도 코드**다(13페이지, 3,666줄).
그래서 한국어 쪽을 고쳐도 영어가 안 따라오고, 두 사이트의 내용이 계속 벌어진다.

| 항목 | 실측(2026-08-23) |
|---|---|
| 한국어 공개 페이지 | 116개 |
| 영어(`/en`) 페이지 | 13개 (11%) |
| 전 페이지 서버 컴포넌트 | 144/144 |
| i18n 라이브러리 | 없음 |
| `toKoreanTeamName` 호출 | 690곳 |
| `toKoreanPlayerName` 호출 | 140곳 |

## 결정

**자동 생성 미러 방식.** 변환 스크립트가 한국어 `page.tsx` 를 읽어
한글 문구·한글화 함수·내부 링크를 영어로 치환한 `/en/**` 파일을 생성한다.
한국어를 고치면 스크립트를 다시 돌려 영어를 재생성한다.

**대상은 SEO 핵심 29개 페이지.** 기존 수동 `/en` 13개는 건드리지 않는다
(품질이 이미 확보돼 있고, 자동 생성으로 덮으면 퇴행 위험).

### 채택하지 않은 안

- **정공법 i18n** — 소스 1벌이 두 언어를 렌더. 구조는 가장 깨끗하나
  1,252개 파일 / 28,700줄을 손봐야 해서 1인 운영 규모를 넘는다.
- **수동 확장 지속** — 지금 방식. 벌어지는 문제가 그대로 재발한다.
- **클라이언트 번역 위젯** — SEO 가치 없음. 이 작업의 목적과 반대.

## 변환 규칙 (스크립트가 하는 일)

1. 한글 문자열 리터럴·JSX 텍스트 → 영어 사전으로 치환
2. `toKoreanTeamName(x)` → `toEnglishTeamName(x)`, `toKoreanPlayerName(x)` → `x`
3. 내부 링크 `/xxx` → `/en/xxx` (영어판이 있는 경로만, 없으면 한국어로 유지)
4. `LEAGUE_DISPLAY` → `LEAGUE_DISPLAY_EN`
5. canonical / hreflang 반전 (`koEnLanguages` 인자 순서)
6. 주석은 한국어 그대로 둔다 (렌더 결과에 영향 없음)

## 성공 기준

- `npx tsc --noEmit` 통과
- 생성된 페이지에 한글이 **렌더 경로상** 0줄 (주석 제외)
- 로컬 dev 에서 29개 라우트 전부 200 응답, 육안 확인
- 한국어↔영어 hreflang 상호 연결
- sitemap 등재 + IndexNow 제출

## 단계

| 단계 | 내용 | 검증 |
|---|---|---|
| 0 | 계획·체크리스트·노트 작성 | 이 문서들 |
| 1 | 변환 스크립트 프로토타입 (1페이지) | 생성물이 tsc 통과 + 육안 OK |
| 2 | 한글 문자열 추출 → 사전 구축 | 사전 JSON, 미번역 0건 |
| 3 | 29개 일괄 생성 | tsc 통과 |
| 4 | 라우트 200 확인 + hreflang + sitemap | dev 서버 실측 |
| 5 | 커밋·배포 | production 확인 |

## 알려진 함정

- **DB에서 나오는 한글은 소스 치환으로 안 잡힌다** (기사 본문, 한글화된 팀명·선수명).
  별도 처리 필요 — 1차 범위에서는 UI 라벨만 다룬다.
- **한글 조사 처리**(`josa()`) 가 붙은 동적 문장은 영어에서 불필요.
  단순 치환하면 어색해지므로 개별 확인 대상.
- 템플릿 리터럴 안 한글은 정규식으로 잡으면 오작동. AST 로 처리한다.
