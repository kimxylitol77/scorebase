# 웹 푸시 킥오프 알림 — 결정과 근거

## 왜 웹 푸시인가
진단(2026-07-30): 랜딩 12,747건/31일 중 회원 전환 0.27%, 재방문 5~13%. 회원 텔레그램 알림은 있지만 회원 93명이 전부다. 가입 없이 걸리는 재방문 갈고리가 없다. 웹 푸시는 브라우저 권한 1클릭이 전부라 전환 장벽이 가장 낮다.

## 설계 결정
- **별표 = 알림 대상.** 새 UI 개념을 만들지 않고 기존 별표(즐겨찾기)에 얹는다. 회원 텔레그램 알림도 "즐겨찾기 한정"이라 멘탈 모델이 같다. 벨 토글은 FavoriteMatches 헤더에만 — 별표가 하나도 없으면 안 보이는 게 맞다(별표가 선행 행동).
- **v1 은 킥오프만.** 골·종료 알림은 발송량·피로도 문제라 반응 보고 확장.
- **구독 동기화는 전체 교체(PUT 방식).** fav-server-sync 와 같은 패턴 — 클라이언트가 별표 전체 집합을 보내고 서버가 교체. 증분 diff 보다 단순하고 레이스에 강하다. 서버가 SCHEDULED·미래 7일 내로 필터하니 클라이언트를 신뢰하지 않는다.
- **크론 */10 + 창 15분.** 매치는 unsent row 만 잡으므로 중복 발송 없음. 킥오프 5~15분 전 도착. 텔레그램 크론(*/2)에 얹지 않은 이유 — 그쪽은 회원·골 실시간이라 결이 다르고, 실패 격리.
- **410/404 Gone → 구독 즉시 삭제.** 브라우저가 구독 만료시키면 endpoint 가 영구 죽음. failCount 는 5xx 일시 오류용(3회 누적 시 삭제).

## 함정
- **iOS Safari 는 홈 화면 추가(PWA) 상태에서만 푸시 가능.** 지원 감지(`PushManager in window`)로 미지원 브라우저에선 벨 자체를 숨긴다 — 눌렀는데 안 되는 것보다 낫다.
- **localhost 는 secure context** 라 로컬 E2E 가능. 프로덕션은 HTTPS 라 문제없음.
- **VAPID 키는 빌드타임 공개키**(NEXT_PUBLIC_) — Vercel env 등록 전 배포하면 벨이 숨겨질 뿐 깨지진 않게 가드.
- matchId 는 Match.id(Int). orphan 카드(DB 미적재)는 별표해도 알림 대상이 못 된다 — 서버 필터에서 자연 제외.

## 효과 측정 (배포 후)
- PushSubscription 수 (주간)
- 재방문율: 진단 스크립트 재실행 — 채널별 2일 이상 세션 비율 (기준선 5~13%)
- 알림 클릭 → /live 유입은 notificationclick 의 utm_source=push 로 식별
