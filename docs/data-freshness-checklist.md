# 데이터 결손 감시 (data-freshness) — 체크리스트

`/api/cron/data-freshness` · 하루 2회(UTC 01:00·13:00 = KST 10:00·22:00)

## 배경

2026-08-14, 선수 경력표가 2017/2018 에서 끊긴 채 며칠 서빙됐다. api-sports 가 분당 한도 초과를 HTTP 200 + `errors` 객체로 답하는 걸 빈 데이터로 삼켜, 시즌이 통째로 빠진 결과가 캐시에 굳은 것이다. 발견은 사용자 눈이었다. 기존 감시는 전부 "응답이 오나 · cron 이 돌았나"를 봐서 이런 결손을 못 잡는다.

## 감시 축

- [x] `career_gap` — 몸값 상위 12명 표본, 경력 최신 시즌이 현 시즌보다 2시즌 이상 뒤처진 비율 ≥ 25% & 3명 이상
- [x] `score_missing` — 종료 6h+ 매치 중 점수 없음 비율 ≥ 3% (최근 7일, 최소 50경기)
- [x] `prediction_gap` — 예측 지원 리그의 킥오프 2h 이내 매치 커버리지 < 50% (최소 8경기)
- [x] `market_value_stale` — 몸값 피드 최신 갱신 > 48h
- [x] `standings_stale` — 시즌 중 정규리그 순위 정체 > 72h 가 3개 이상, 또는 하나라도 > 168h
- [x] `injuries_empty` — 소스가 있는 축구 리그(빅5·MLS)에서 부상자 있는 팀이 2팀 이하
- [x] `reschedule_dup` — 같은 대진(비야구)이 12시간 안 간격으로 SCHEDULED/LIVE 2행+ = 연기 추종 시차 유령 (2026-08-16 라리가 유령 카드 사건 재발 감지용, 기준선 0·하키 친선 백투백 21h 는 게이트 통과)
- [x] `lol_leaders_stale` / `lol_leaders_shrink` — 시즌 중(최근 14일 LCK 종료매치 있음)인데 LeagueLeader LOL 갱신 > 60h, 또는 행 수 < 15 (2026-08-15 신설 — BDL 키 사망 두 달 동결 재발 방지)
- [x] 축 하나가 예외로 죽어도 나머지 점검은 계속 (`*_check_failed` 로 보고)
- [x] CRON_REGISTRY 등록 — 감시 자체가 멈추면 cron-freshness 가 잡는다

## 축구 부상자 소스 규칙 (2026-08 확정 — 매번 다시 판단하지 말 것)

1. **TheSports 가 정본.** 경기 출전명단에 딸린 결장자 목록이라 사유·시작일·결장 경기수가 확정값이다. api-football 은 경기별 결장 플래그를 묶은 추정이라 정확도가 낮다.
2. **판정은 팀 단위.** 그 팀의 최근 경기 명단을 읽었으면 ts 결과를 쓴다 — 부상자 0명도 "결장자 없음" 이라는 확정 정보다.
3. **명단을 못 읽은 팀만** api-football 로 보강한다.
4. **둘 다 없으면 0명이 아니라 "확인 불가".** 화면에 "부상 정보 미제공 N팀" 으로 따로 뺀다. af 는 리그·시즌별 `coverage.injuries` 가 꺼져 있으면 통째로 0건을 주므로(2026-08 실측: 빅5·K리그·J리그 2026 = off, MLS = on) 이걸 "부상자 없음" 으로 그리면 사용자는 사이트가 고장난 줄 안다.
5. **출처 라벨은 실제 기여분으로 적는다.** "af 를 호출했나" 가 아니라 "af 가 실제로 팀을 채웠나".

리그별 커버리지는 소스 품질 문제이지 우리 버그가 아니다 — ts 는 EPL 경기당 10명씩 싣지만 K리그·사우디는 거의 안 싣는다(2026-08 실측: 최근 경기 기준 K리그1 1건·K리그2 0건). 명단을 읽었는데 비어 있으면 규칙 2에 따라 0명으로 표기한다.

| 축 | 임계 | 실측(추가 시점) | 근거 사고 |
|---|---|---|---|
| `cross_sport_mapping` | 1건 이상 | DB 0 · JSON 0 · 매치 0 | ISRAEL_PL 하포엘 예루살렘이 **농구** row 를 가리켜 8/23 경기 홈팀이 농구 클럽으로 나가고 있었다 |
| `league_exposure_gap` | 향후 45일 3경기+ & ALL_LEAGUES 미등록 | 0건 | BRASILEIRAO_2 가 43경기·20팀·순위 20행을 매일 수집하면서 `/leagues/BRASILEIRAO_2` 404·예측 0 (8/16 진단 후 8/21 까지 방치) |

**`cross_sport_mapping` 의 핵심 — "SOCCER_LEAGUES 에 없으면 비축구" 로 판정하지 말 것.**
BRASILEIRAO_2 처럼 축구인데 그 집합에서 빠진 코드가 실제로 있어서, 그렇게 짜면 정상 데이터가
매일 오탐으로 잡힌다(8/21 실측: 그 방식으로 코파 두 브라질 4건이 걸렸고 전부 오탐).
`BASEBALL/BASKETBALL/HOCKEY/VOLLEYBALL/LOL/MMA_LEAGUES` 합집합에 **명시적으로 속하는가**로만 본다.

**매핑은 두 곳에 산다.** DB `TeamSourceId` 와 저장소 `team-id-mapping.json`. 매치 수신 라우트가
DB 를 먼저 보고 없으면 JSON 으로 폴백하므로 **양쪽 다** 봐야 한다 — 이스라엘 건은 DB 엔 없고
JSON 에만 있어서 DB 만 보면 못 잡는다.

**`league_exposure_gap` 의 오탐 게이트** — 내린 리그의 잔존 행이 걸리지 않게 향후 45일 경기 수
하한(3건)을 둔다. 의도적으로 내렸는데 수집이 계속되면 `EXPOSURE_GAP_EXEMPT` 에 넣는다.

## career_gap 오탐 — af 예산 가드와의 설계 충돌 (2026-08-21)

프로덕션 알림 `career_gap 12/12` 가 왔는데 **실제 선수 페이지는 정상**이었다(라민 야말
프레시 렌더에서 2025/2026 라리가 28경기 16골 정상 표시).

원인은 데이터 결손이 아니라 **예산 가드**다.
`fetchPlayerCareer` 는 선수당 최대 13콜이라 `PLAYER_RENDER_DAILY_CAP`(15,000) 를 넘으면
`requirePlayerPageQuota()` 가 **일부러 throw** 한다(8/19 쿼터 소진 사고 후 도입, 빈 표가
24h 캐시에 굳는 걸 피하려는 의도적 설계). 그런데 소비처가
`getCachedCareer(afId).catch(() => [])` 로 삼켜서 **"조회 거부"와 "데이터 없음"이 구분되지 않는다.**

실측 — 그날 예산 18,184/15,000 초과(af-pro:players 10,761 + injuries 6,633 + players/seasons 790).

→ `playerRenderBudgetOk()` 를 export 하고, 예산이 없으면 축을 건너뛴다
(`{sampled:0, stale:0, skipped:"af-player-budget"}`). **측정이 불가능한 시간대는 알리지 않는다.**

⚠ 이 축이 다시 울리면 **먼저 예산부터** 보라. 예산이 남아 있는데 울렸다면 그때가 진짜다.
